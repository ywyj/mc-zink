# 测量方法

本文记录 DSH-Zink 的测量协议、原始数据、三项优化的测量设计与置信度。所有结论只对**本机、本驱动、本场景**负责。

## 一、测试环境

| 项目 | 值 |
|---|---|
| CPU | AMD Ryzen 7 5800H |
| GPU | NVIDIA RTX 3060 Laptop |
| 驱动 | 596.21 |
| 系统 | Windows 10/11 x64 |
| 分辨率 | 1920×1080 |
| 游戏 | Minecraft 1.21.1 + NeoForge 21.1.229 |
| 场景 | 超平坦世界「新的世界」 |
| 光影 | 关闭 |
| mod 数量 | 56 |
| 电源 | 插电，高性能模式；必须记录功率、时钟、温度、限频状态 |

**电源状态不是可选项**。电池态会触发 NVIDIA Battery Boost 的 30 帧硬锁，此时测到的不是渲染性能，而是省电策略。

## 二、指标定义

### 采样

- 以 **1Hz** 记录帧率（每秒一个样本）；
- 首个有效样本通常在启动后 63–75 秒出现（世界加载、着色器编译结束）；
- 每轮要求至少 **120–122 个样本**（`needSamples`），变异系数上限 0.9（`cvMax`）；
- 取每轮**末窗口**（`tailN = 30`）的样本计算中位数、p10、p90 和变异系数。

### pooled median

把同一队列在**多轮**中的末窗口中位数再取中位数，得到一个抗单轮噪声的代表值。它不是把所有样本混在一起算，而是“先每轮取中位，再跨轮取中位”，避免某一轮采样过长主导结果。

### 比值

```text
ratio = zink 队列的 pooled median / 原生 OpenGL 队列的 pooled median
```

**只在同一轮交错队列内比较**。不同批次、不同电源状态、不同驱动版本的绝对值不可比。

## 三、queue_final 协议

### 设计

- **3 个变体**：
  - `A0`：zink + shader cache + E-A；
  - `B`：zink + zoo1 + P3（`NO_FB_WAIT`）+ E-A；
  - `N`：原生 NVIDIA OpenGL + E-A。
- **9 轮交错**，顺序为 `A0 → B → N → A0 → B → N → A0 → B → N`，每轮之间重启游戏客户端，避免上一轮的热缓存/热状态污染下一轮。
- **E-A 全局生效**：三个变体都应用 E-A，确保比较的是“zink 与原生”的差异，而不是“有没有 E-A”。
- 每轮记录 loader（native / zink）、powerInfo、同队列对照，三者缺一不得用于 A/B 结论。

### 原始数据

| 轮次 | 队列 | 末窗口中位（帧/秒） |
|---:|---|---:|
| 1 | A0a | 156 |
| 2 | B（NO_FB_WAIT） | 168 |
| 3 | N（原生） | 193 |
| 4 | A0b | 193 |
| 5 | B（NO_FB_WAIT） | 188 |
| 6 | N（原生） | 212 |
| 7 | A0c | 182 |
| 8 | B（NO_FB_WAIT） | 194 |
| 9 | N（原生） | 213 |

### 汇总

| 队列 | pooled median | 相对原生 |
|---|---:|---:|
| zink + cache + E-A（A0） | **182** | **0.858** |
| zink + zoo1 + P3 + E-A（B） | **188** | **0.887** |
| 原生 NVIDIA OpenGL + E-A（N） | **212** | 1.000 |

### 为什么第一块偏低

按轮次分三块计算 A0 / N：

| 块 | A0 | N | 比值 |
|---|---:|---:|---:|
| 第 1 块（第 1、3 轮） | 156 | 193 | 0.808 |
| 第 2 块（第 4、6 轮） | 193 | 212 | 0.910 |
| 第 3 块（第 7、9 轮） | 182 | 213 | 0.854 |

第一块明显受**冷启动慢热**影响：客户端刚启动、着色器缓存未热、JIT（即时编译）未稳定。第 2、3 块更接近稳态。综合三块与 pooled 值，对外取：

> **zink ≈ 0.88 ± 0.03 原生 OpenGL（差距约 12%）**。

### 与历史数字的关系

- 早期记录 0.63–0.71：窗口被遮挡、后台限速、不同采样窗口，协议不同，**作废**；
- 更早的 0.555：电池/降频状态下的单次测量，**作废**；
- 中途曾出现 0.9305（同队列 ABBA，E-B 默认开启时）与 0.9656 / 0.9958（PGO 队列）：测量期不同、默认项不同，**不与 queue_final 混用**。对外统一引用 0.88 ± 0.03，并注明测量期。

## 四、噪声底

必须先知道“多大的差异才算差异”：

- 同配置 `A0 vs A0` 的一次对照曾差 **7% ~ 12%**；
- 因此单轮差异 **±5% ~ ±8%** 一律视为噪声；
- 只有 **> 10%** 且能在第二个队列/第二次运行复现的差异，才判为真实收益；
- 跨队列的绝对值不可比，只比同一交错队列内的比值。

## 五、E-A：ImmediatelyFast 关闭 `fast_buffer_upload`

### 假设

ImmediatelyFast 开启 `fast_buffer_upload` 时，小尺寸 `glBufferSubData` 会走 Mesa 的 `u_upload` 暂存缓冲，再额外发一次 `vkCmdCopyBuffer`；关闭后改走 `glBufferData(DISCARD_WHOLE_RESOURCE)` 的整块重分配快路径。后者在 zink 上应该更快。

### 测量设计

| 测量 | 设计 | 结果 |
|---|---|---|
| P1 | 同场景 A/B，含漂移校正 | +21.5%（被污染，明显夸大） |
| P1b | 重新交错，缩短单轮时长 | +4.0%（原始值 +7.6%） |
| 机制反推 | 每帧 76–81 次上传 × 约 9.5 微秒 | 0.73–0.77 毫秒/帧 |

### 旁证

GL 调用计数（200 帧尾窗）：

- E-A 生效前：`glBufferSubData` 80–81 次/帧，其中 76 次来自 ImmediatelyFast；
- E-A 生效后：`glBufferSubData` 站点全部归零，`GlStateManager._glBufferData` 升至 68.24 次/帧。

调用真的换了路径，不只是“看起来快了”。

### 结论与置信度

- 对外口径：**+4% ~ +8%**（取 P1b 与机制反推的交集，不采用被污染的 +21.5%）；
- 置信度：**高**。多队列重复、计数器旁证、代码路径明确。

## 六、E-B：AcceleratedRendering 关闭缓冲区绑定恢复

### 假设

`block_buffer_binding_restoring` 每帧用 `glGetIntegeri_v` 查询并恢复缓冲区绑定，约 89 次/帧；这些查询在 zink 上要经过翻译与状态校验，是纯开销。

### 测量设计

| 测量 | 设计 | 结果 |
|---|---|---|
| P1 | 同场景 A/B | +12.8% |
| P1b | 重新交错 | +4.5% |
| 机制反推 | 89 次 × 单价 | 0.40 毫秒/帧 |

### 旁证

- 两条统计站点（1275 / 1276）从 89 次/帧降到 0；
- 总 GL 调用从 2168 次/帧降到 2055 次/帧。

### 为什么没进默认

关闭后，渲染正确性依赖“裸状态”恰好正确。开光影的 6 场景截图门禁（`shaders/eopt/SMOKE_SHADERON_CHECKLIST.md`，本机工作区文件，未随公开快照）**未通过**。没有通过门禁的正确性证据，收益再高也不能默认开启。

### 结论与置信度

- 对外口径：**+4% ~ +5%**（保守，取两次测量的较低值）；
- 置信度：**中**。收益方向一致，但正确性门禁未过，且只有两次有效测量。

## 七、P3：删除 frontbuffer flush 的 fence 等待

### 假设

`zink_flush_frontbuffer()` 在提交当前帧后等待 `flush_completed` fence。该改动与 Mesa 上游提交 `33f0fecc` 等价，假设这次等待不再必要，去掉它应当能减少提交线程的阻塞。

### 测量设计

| 测量 | 设计 | 结果 |
|---|---|---|
| mix1 | 3 个变体交错 | +2.0% ~ +3.6% |
| queue_final | 相邻配对（同块内 B 对 A0） | +7.7% / −2.6% / +6.6%，中位 +6.6% |
| 上游等价 | 与 Mesa 提交 `33f0fecc` 语义一致 | — |

相邻配对的三次结果里有一次为负（−2.6%），落在噪声区间内；中位 +6.6%，与 mix1 的方向一致。对外取保守值 **+2% ~ +4%**。

### 结论与置信度

- 置信度：**中高**。两个独立场景、方向一致、补丁语义与上游提交等价；但单次配对波动较大，故不取 +6.6% 作为对外数字。

## 八、归因：差距到底在哪

### GL 调用画像（稳态，200 帧尾窗）

| 类别 | 次/帧 | 单价 | 折合每帧 |
|---|---:|---:|---:|
| 纹理（tex） | 673 | 80 纳秒 | 54 微秒 |
| uniform | 663 | 192 纳秒 | 127 微秒 |
| 绑定（bind） | 481（其中 useProgram 129） | 289 纳秒 | 139 微秒 |
| 绘制（draw） | 91 | 1.75 微秒 | 159 微秒 |
| pixelStorei | 61 | — | — |
| 同步（sync） | ≈105 | — | — |
| 其他 | ≈90 | — | — |
| **合计** | **2168** | — | — |

`glBindTexture` 在 zink 上 28.2 纳秒，原生 38.4 纳秒——单次调用 zink 并不慢。差距集中在**少数重型调用与内部等待**，而不是“每次调用都慢一点”。

### fence 等待

- `glClientWaitSync` 每帧 1 次，传入 `INFINITE`，等待 `fence_finish`；
- `zink_screen_timeline_wait` 约 333 微秒，折合 355 微秒/帧，约 **7.7% 墙钟**；
- 但加深管线（H2b）与深队列都判负，说明 CPU 吞吐受限，这段等待不是可以简单回收的“死时间”。

### 资源画像

- Java 3D 引擎占 29.7% ~ 32.8% CPU；
- Java 进程约 400% CPU（4 核）；
- GPU 远非瓶颈（无光影、1080p、超平坦）。

这也解释了为什么 CPU 侧的 E-A / E-B 有效，而 GPU 侧优化（超分、帧生成）收益有限。

## 九、被否决方案的测量

| 方案 | 结果 | 判读 |
|---|---:|---|
| `ZINK_DEBUG=noopt` | −18% ~ −27% | 关闭优化后显著变慢，确认 zink 优化路径有效 |
| `GALLIUM_THREAD=0` | −13% ~ −18% | 单线程 Gallium 更慢 |
| `flushsync` | −6% ~ −14% | 强制同步拖慢 |
| `ZINK_DESCRIPTORS=lazy` | 无收益 | 在噪声内 |
| `ZINK_DEBUG=rp` | 无收益 | 在噪声内 |
| kopper 同步 present（P1 / P4） | −1.5% ~ −4% | 同步呈现更慢 |
| P2 batch 窗口 5 → 12 | 无收益 | 加宽窗口没有帮助 |
| Mesa 26.3.0-rc1 整树 | +0% ~ +2.5% | 噪声内，不采纳 |
| H2b 管线深度 | −2.8% | 判负 |
| Sodium render-ahead 4 → 32 | −5% ~ −6% | 判负 |
| glthread | −2.8% ~ −5.2% | 判负 |
| LTO | +1.1% ± 1.2% | 噪声内 |
| PGO | +8.2%（历史） | 后续基线已含，最终队列未再用 |

## 十、置信度汇总

| 结论 | 置信度 | 依据 |
|---|---|---|
| zink ≈ 0.88 原生 | 高 | 9 轮交错、原生对照、三块比值一致；仅限本机 |
| E-A +4% ~ +8% | 高 | 两次测量 + 计数器旁证 + 代码路径 |
| E-B +4% ~ +5% | 中 | 两次测量方向一致；正确性门禁未过 |
| P3 +2% ~ +4% | 中高 | 两场景方向一致；单次配对有波动 |
| 旧 0.63–0.71 作废 | 高 | 协议不同（遮挡/限速/采样窗口） |
| 光影口径 0.78 作废 | 高 | 测量时 GPU 处于 P8 210MHz 降频态 |

## 十一、复现要点

完整步骤见 [REPRODUCE.md](REPRODUCE.md)。最少需要：

1. 同一台机器、同一驱动、同一场景、同一 mod 列表；
2. 一个能按 1Hz 记录帧率的采样器（本项目的 `bench3` 未随公开快照，可用任意等效工具）；
3. 原生 OpenGL 与 zink 两套 loader，交替启动；
4. 电源、温度、频率记录；
5. 至少 3 轮交错，每轮 ≥ 120 个样本，取末 30 帧中位数。

没有原生对照、没有电源记录、没有同场景的“加速比”，不应当作结论使用。
